# Combined offline receive engine

`experimental/zz_eth_packet_engine.v` connects the AXI-Lite adapter, registered
mailbox, two-bank packet core and single-owner foreground/prefetch arbiter in one
100 MHz clock domain. The wrapper is an integration and measurement target. It
is not instantiated by the live MNTZorro module, connected in the block design,
or part of a firmware image. No live register address is allocated.

## Ownership boundaries

The ARM-facing AXI-Lite aperture uses the relative offsets in [AXILITE.md](AXILITE.md).
All accepted control transactions belong to its adapter until their responses
retire. `local_drained` has exactly that local meaning. It says nothing about
upstream posted commands or either AXI read client.

The mailbox is the registered descriptor producer. Its immutable pending record
feeds the packet core, and the core's release record feeds the mailbox's held
snapshot. The ARM lease helper still owns DDR slot reuse; no slot is freed merely
because a fill or host ACK completed.

All physical read traffic goes through `zz_eth_read_arbiter`. Foreground demand
has priority when idle, and `foreground_pending` reserves an impending demand
DDR read. A host read waiting for its packet must not assert this hint: its fill
must be allowed to proceed. Once a physical AR is selected it cannot be revoked;
late demand waits for that burst's accepted RLAST. Response routing follows the
latched owner, never the response ID.

Foreground ARCACHE/ARPROT/ARID are passed intact. Packet attributes are wrapper
parameters (default ARCACHE 0xf, ARPROT 0, ID 0); production integration must
check the actual interconnect/cache policy. Tests use deliberately different
foreground/packet attributes and ID widths 1 and 2 to expose incorrect wiring.
These distinct test values do not propose a live cache-policy change.

`flush_request` reaches the mailbox/core only. It never resets the shared arbiter.
An unaccepted packet AR already asserted by the core survives cancellation,
including while a foreground transaction owns the physical port, and must later
be accepted and drained. Conversely, the packet core can finish its own flush
while a foreground response is still outstanding. `core_flush_done` is only the
packet-core completion pulse; the mailbox consumes it on the following edge.
It is not a global idle or ring-reuse signal. All upstream, GEM and host fences
from the ARM/reset contracts remain external integration obligations.

Only coordinated `aresetn` resets all four components and their connected AXI
endpoints. A logical Amiga reset must follow control/upstream drain, then packet
flush/drain, with the other required fences before rebuilding or rearming.

## Validation

Run `python3 test/eth_packet_window/run.py --engine --id-width 1` and repeat with
ID width 2. The actual wrapper runs the five AXI-Lite groups plus three integrated
cases: foreground reservation/response backpressure with an independent local
bank read; packet-selected stalled AR plus a 25 us delayed tail during flush,
followed by a live foreground response after packet drain; and foreground-selected
stalled AR with a queued packet cancellation that drains later, then fresh-session
recovery. Per-client requests/responses balance at 4/4 foreground and 5/5 packet.
Five descriptors are accepted, three released normally and two cancelled by flush.

The test checks physical AR stability, exclusive response routing, attributes,
IDs, exact control writes, release snapshots and recovery. Four injected wiring
faults (logical flush resetting the physical owner, lost foreground reservation,
crossed cache attributes, and physical ARREADY wired directly to the core) fail.
The direct core, standalone mailbox/AXI-Lite and shared-port regressions also pass.
This is not an ARM/interconnect, host-driver or Zorro-pin test.

The [OOC probe](OOC.md) now has `--top engine`, with the real registered producer
inside the timing graph and explicit mailbox-to-core cookie setup/hold reports.
The core profile remains available. Actual resource/timing reports must identify
which profile was measured; neither profile establishes full-design timing or
hardware throughput. No bitstream is generated by either probe.
